# บทที่ 5 สรุปผลการดำเนินงานและข้อเสนอแนะ

> ร่างโดย thesis-writer — สรุปจากโค้ดใน `dashboard/` และ `apps-script/` และผลทดสอบในบทที่ 4 เท่านั้น ไม่มีผลจากการใช้งานจริง ส่วนที่รอผลหลัง deploy ระบุเป็น `[รอใส่: ...]`

## 5.1 สรุปผลการดำเนินงาน

โครงงานนี้พัฒนาระบบติดตามคดีส่งตรวจพิสูจน์ DNA ที่ต่อยอดจาก Google Sheets ที่กลุ่มงานใช้อยู่ ประกอบด้วย Dashboard บนเว็บ แชตบอต LINE และรายงานสรุปอัตโนมัติ ทั้งหมดอยู่ในโปรเจกต์ Google Apps Script เดียวกันและใช้บริการในระดับที่ไม่มีค่าใช้จ่าย ผลการดำเนินงานเทียบกับวัตถุประสงค์ในหัวข้อ 1.2 มีดังนี้

1) **Dashboard (วัตถุประสงค์ข้อ 1)** พัฒนาแล้ว Dashboard ต้นแบบถูกย้ายมาให้บริการผ่าน HtmlService อ่าน Sheet ฝั่งเซิร์ฟเวอร์ด้วย SpreadsheetApp แทนการอ่านจากเบราว์เซอร์ Sheet จึงไม่ต้องเปิดแชร์แบบสาธารณะ หน้าเว็บแสดงสถิติแยกตามเดือน ปี จังหวัด สถานี ประเภทคดี และผู้ตรวจ คดีที่ยังไม่รับผลแยก 2 กลุ่ม ระยะเวลาดำเนินการ หน้าตรวจสอบข้อมูล และข้อมูลห้องปฏิบัติการ (ภาพรวม งบประมาณ และ Lot พัสดุ) การเข้าถึงจำกัดด้วยการควบคุมสิทธิ์ 2 ชั้น คือ อีเมลต้องอยู่ในแท็บ “ผู้ใช้” ซึ่งตรวจทุกครั้งที่ขอข้อมูล และผู้ใช้ต้องได้รับแชร์ Sheet แบบผู้มีสิทธิ์อ่าน ผลทดสอบด้วยข้อมูลจำลองแสดงว่าทุกเมนูแสดงผลได้ทั้งบนคอมพิวเตอร์และโทรศัพท์ และการตรวจสิทธิ์ปฏิเสธทุกกรณีที่เงื่อนไขไม่ครบ (ตารางที่ 4.2 และ 4.4) ส่วนการเปิดด้วยบัญชี Google จริงยังรอการนำขึ้นใช้งาน
2) **แชตบอต LINE (วัตถุประสงค์ข้อ 2)** พัฒนาแล้ว บอตตอบสถานะคดีจากเลข บก. และสรุปคดีค้างโดยแยกจำนวน “กำลังดำเนินการ” และ “เสร็จแล้ว รอรับผล” ตอบเฉพาะกลุ่มที่อนุญาต และเงียบเมื่อข้อความไม่ได้เรียกบอต การแยกเจตนาใช้กฎในโค้ดเป็นหลัก และส่งเฉพาะข้อความคำถามที่ตัดตัวเลข ชื่อ อีเมล URL และคำที่ระบุสถานีออกแล้วไปให้ Gemini เมื่อกฎไม่เข้าใจ คำตอบสร้างจากโค้ดเองโดยไม่ส่งข้อมูลคดีออกไป ผลทดสอบยืนยันว่าเนื้อหาที่ส่งไปยัง Gemini ไม่มีค่าจาก Sheet (หัวข้อ 4.5.1) แต่ยังไม่ได้ทดสอบกับ LINE และ Gemini จริง และยังไม่ได้วัดความแม่นยำของการแยกเจตนา
3) **รายงานสรุปอัตโนมัติ (วัตถุประสงค์ข้อ 3)** พัฒนาแล้ว ตัวตั้งเวลารายวันส่งสรุปเดือนปฏิทินก่อนหน้าในวันที่ 1 ของเดือน (ส่งตามหลังได้ถึงวันที่ 3 เมื่อส่งไม่สำเร็จ และไม่ส่งซ้ำ) และในวันที่ 1 มกราคมส่งสรุปปีปฏิทินก่อนหน้าในคำขอเดียวกัน เนื้อหามีจำนวนคดี จำนวนของกลาง จำนวนคดีแยกประเภท และจำนวนคดีของผู้ตรวจแต่ละคนแยกตามประเภท โดยไม่มีเลขคดี ตัวเลขคำนวณด้วย `Stats.gs` ชุดเดียวกับที่ใช้ตอบในแชตบอต และผลทดสอบแสดงว่าตรงกับ Dashboard และค่าที่คำนวณอิสระด้วย Python ทุกค่า (ตารางที่ 4.3) การส่งเข้ากลุ่มจริงถูกปิดไว้จนกว่าเจ้าของโครงงานจะอนุมัติ (`PUSH_ENABLED`)
4) **การทดสอบ (วัตถุประสงค์ข้อ 4)** บรรลุในขอบเขตของข้อมูลจำลองและบริการจำลอง ชุดทดสอบอัตโนมัติผ่าน 96 จาก 96 กรณี และการทดสอบข้อมูลจำลองกับ Dashboard ต้นแบบผ่าน 18 จาก 18 กรณี รวม 114 กรณี ครอบคลุมความถูกต้องของการคำนวณ การควบคุมสิทธิ์ และการคุ้มครองข้อมูลส่วนบุคคล ข้อจำกัดของผลทดสอบสรุปไว้ในหัวข้อ 4.6.2

กล่าวโดยสรุป ระบบพัฒนาครบตามขอบเขตในหัวข้อ 1.3 และผ่านการทดสอบด้วยข้อมูลจำลองแล้ว แต่ยังไม่ได้นำขึ้นใช้งานกับข้อมูลจริงและกลุ่ม LINE จริง ประโยชน์ที่คาดว่าจะได้รับในหัวข้อ 1.4 เช่น การลดเวลาค้นหาสถานะคดีและการลดความคลาดเคลื่อนของรายงาน จึงยังเป็นผลที่คาดไว้ ยังไม่ได้วัดจริง

[รอใส่: ผลการนำระบบขึ้นใช้งานจริงและผลการทดลองใช้กับเจ้าหน้าที่ ถ้ามี (ดูหัวข้อ 4.7)]

## 5.2 ปัญหาและอุปสรรค

1) **คุณภาพข้อมูลต้นทาง** ณ วันที่ได้รับโครงสร้างไฟล์ คอลัมน์ “ประเภทคดี (เลือก)” และ “ผู้ตรวจ (เลือก)” ใน Sheet จริงกรอกไว้เพียงส่วนน้อยของแถวทั้งหมด (หัวข้อ 3.2.4) สถิติแยกประเภทและแยกผู้ตรวจ ทั้งบน Dashboard และในรายงานรายเดือน จึงจะเป็นกลุ่ม “ไม่ระบุ” เกือบทั้งหมดจนกว่าจะกรอกข้อมูลเพิ่ม ระบบแก้ได้เพียงการแสดงกลุ่ม “ไม่ระบุ” อย่างชัดเจนแทนการตัดแถวทิ้ง แต่แก้ที่ต้นเหตุไม่ได้
2) **ข้อจำกัดในการระบุตัวผู้ใช้บัญชี Gmail** การ deploy แบบ Execute as: Me ซึ่งไม่ต้องแชร์ Sheet ให้ผู้ใช้ อ่านอีเมลของผู้ใช้ที่อยู่นอกโดเมน Google Workspace ของเจ้าของสคริปต์ไม่ได้ [12] จึงตรวจรายชื่อไม่ได้ (หัวข้อ 3.4.1) โครงงานจึงต้องเปลี่ยนเป็นแบบ User accessing the web app ร่วมกับการแชร์ Sheet แบบผู้มีสิทธิ์อ่าน ข้อเสียคือผู้ใช้ในรายชื่อเปิด Sheet ต้นฉบับได้โดยตรงและเห็นทุกคอลัมน์ ผู้ดูแลต้องปรับสิทธิ์ 2 ที่ทุกครั้งที่เพิ่มหรือถอนผู้ใช้ และผู้ใช้ต้องผ่านหน้าขออนุญาตของแอปที่ยังไม่ผ่านการตรวจสอบของ Google (หัวข้อ 3.4.3)
3) **ตรวจลายมือชื่อ webhook ไม่ได้** `doPost` ของ Apps Script ไม่ได้รับส่วนหัวของคำขอ จึงตรวจ `x-line-signature` ตามที่ LINE กำหนดไม่ได้ [15], [22] โครงงานใช้มาตรการทดแทน เช่น รหัสลับใน URL การจำกัดกลุ่ม การตอบด้วย reply token เท่านั้น และการทิ้งเหตุการณ์ซ้ำ (ตารางที่ 3.12) แต่ยังเหลือความเสี่ยงหาก URL ที่มีรหัสลับรั่วไหล นอกจากนี้ Apps Script กำหนดรหัสสถานะ HTTP เองไม่ได้ ปุ่ม Verify ใน LINE Developers Console อาจแสดงข้อผิดพลาดแม้บอตทำงานได้ ซึ่งยังต้องยืนยันเมื่อใช้งานจริง
4) **เงื่อนไขข้อมูลของ Gemini API ระดับฟรี** เงื่อนไขการใช้บริการระบุให้ไม่ส่งข้อมูลอ่อนไหว ข้อมูลลับ หรือข้อมูลส่วนบุคคล [8] การใช้ LLM จึงถูกจำกัดให้แยกเจตนาจากข้อความที่ตัดข้อมูลออกแล้วเท่านั้น และคำตอบทั้งหมดสร้างจากโค้ด ทำให้บอตตอบได้เฉพาะคำถาม 2 ประเภทที่กำหนด การตัดข้อมูลด้วยกฎยังอาจพลาดบางรูปแบบ เช่น ชื่อบุคคลที่ไม่มีคำนำหน้า (หัวข้อ 3.5.2)
5) **การทดสอบโดยไม่มีบริการจริง** ข้อกำหนดด้าน PDPA ของทีมห้ามใช้ข้อมูลจริงในการพัฒนา และการส่งข้อความเข้ากลุ่มจริงต้องรอการอนุมัติ การทดสอบทั้งหมดจึงทำด้วยข้อมูลจำลองและตัวจำลองของบริการ Google, LINE และ Gemini ซึ่งยืนยันตรรกะของโค้ดได้ แต่ยืนยันพฤติกรรมของแพลตฟอร์มจริงไม่ได้ (หัวข้อ 4.1.3)

[รอใส่: ปัญหาและอุปสรรคอื่นที่เจ้าของโครงงานพบระหว่างดำเนินงานหรือระหว่างนำขึ้นใช้งานจริง ถ้ามี]

## 5.3 ข้อเสนอแนะ

### 5.3.1 ข้อเสนอแนะในการนำไปใช้

1) **ทดลองใช้กับเจ้าหน้าที่จริงก่อนใช้งานเต็มรูปแบบ** ติดตั้งตามคู่มือ `apps-script/README.md` แล้วทดสอบรายการในหัวข้อ 4.1.3 กับบัญชีและกลุ่ม LINE จริง ให้เจ้าหน้าที่ทดลองใช้ระยะหนึ่ง และเก็บแบบประเมินความพึงพอใจและความเห็นต่อการใช้งาน Dashboard และแชตบอต
2) **ปรับปรุงการกรอกข้อมูลประเภทคดีและผู้ตรวจ** เช่น กำหนดให้กรอกสองคอลัมน์นี้ตั้งแต่ตอนรับคดีหรือมอบหมายงาน และใช้จำนวนคดีในกลุ่ม “ไม่ระบุ” บน Dashboard เป็นตัวติดตามว่ายังมีคดีที่ไม่ได้กรอกเท่าใด เพื่อให้สถิติแยกประเภทและแยกผู้ตรวจมีความหมาย
3) **แยกคอลัมน์ที่ไม่จำเป็นออกจาก Sheet ที่แชร์** เนื่องจากผู้ใช้ในรายชื่อเปิด Sheet ต้นฉบับได้ ควรย้ายคอลัมน์ที่ไม่จำเป็นต่อการติดตามงาน เช่น เลขหนังสือนำส่ง ไปไว้ในไฟล์ที่ไม่ได้แชร์ หรือให้ Dashboard อ่านจาก Sheet สรุปที่มีเฉพาะคอลัมน์ที่ใช้
4) **ทบทวนการตั้งค่าเป็นระยะ** ได้แก่ รายชื่อในแท็บ “ผู้ใช้” ให้ตรงกับการแชร์ Sheet โควตาข้อความของ LINE Official Account และเงื่อนไขการใช้บริการของ Gemini API ซึ่งอาจเปลี่ยนแปลงได้

### 5.3.2 ข้อเสนอแนะในการพัฒนาต่อ

1) **วัดความแม่นยำของการแยกเจตนา** รวบรวมตัวอย่างคำถามที่เจ้าหน้าที่พิมพ์จริง (หลังตัดข้อมูลส่วนบุคคลแล้ว) เพื่อวัดความแม่นยำของกฎในโค้ดและของ Gemini และใช้ผลปรับกฎหรือคำสั่งระบบ
2) **ใช้โดเมน Google Workspace หรือเซิร์ฟเวอร์ตัวกลาง** ถ้าหน่วยงานมีบัญชี Google Workspace ของหน่วยงาน การ deploy แบบ Execute as: Me ภายในโดเมนเดียวกันจะอ่านอีเมลผู้ใช้ได้ (หัวข้อ 3.4.1) ทำให้ไม่ต้องแชร์ Sheet ให้ผู้ใช้ทุกคน และถ้าต้องการตรวจลายมือชื่อ webhook ตามที่ LINE กำหนด อาจใช้เซิร์ฟเวอร์ตัวกลางที่อ่านส่วนหัวได้ ตรวจลายมือชื่อ แล้วจึงส่งต่อให้ Apps Script ซึ่งต้องพิจารณาค่าใช้จ่ายและผู้ดูแลเพิ่ม
3) **ขยายการแจ้งเตือน** เช่น แจ้งเมื่อคดีค้างนานเกินเกณฑ์ที่กำหนด หรือแจ้งหน่วยงานผู้ส่งเมื่อตรวจเสร็จและพร้อมให้มารับผล ซึ่งต้องพิจารณาโควตาข้อความ push และการคุ้มครองข้อมูลส่วนบุคคลของผู้รับก่อน
4) **ทดสอบด้านประสิทธิภาพ** วัดเวลาตอบของ Dashboard และแชตบอตเมื่อข้อมูลเพิ่มขึ้นหลายปี และการใช้งานพร้อมกันหลายคน เทียบกับโควตาของ Apps Script
5) **เพิ่มการตรวจค่าความลับในโค้ดอัตโนมัติ** เช่น ให้ชุดทดสอบค้นหารูปแบบของ token และ API key ในไฟล์โค้ดก่อน commit เพื่อปิดช่องว่างที่ระบุในหัวข้อ 4.6.1
